# dingtalk-aitable-assistant · 自我进化机制（darwin-lite）

> 本机制在每次任务收尾（P5 复盘）由 WorkBuddy 执行：采集 → 提炼 → 三问筛选 → 用户确认后落地（备份→写入→CHANGELOG→版本+1）。无常驻脚本、无评分表；评委 = 用户本人。

## 一、触发条件（三类）
- **T1 显式纠错**：用户指出结果错误并给出正确值/方向；指出执行偏差；提出新的工作模式或偏好。
- **T2 运行时异常**：执行中出现可复现异常；自验证发现 CLI/平台限制、理论方案落地不符（例：字段对象实为 fieldName/config、公式字段不支持创建）。
- **T3 逻辑覆盖空洞**：遇到未覆盖输入/边界；同类「自我调整自救成功且用户未纠错」累计满 3 次 → 自动升级为候选（计数记在当月 cards 文件"自救事件"区）。

## 二、筛选三问（不满足任一则放弃）
1. **真实发生**：≥1 次实际执行佐证，非想象；
2. **可泛化**：能覆盖未来同类输入，非一次性特例；
3. **不重复**：与现有规则不冲突；冲突时合并或废弃旧规则，交用户决定。

## 二之补、能力基线三原则（用户红线 · 2026-09-23 确立）

> 本节约束**所有**迭代动作（采纳 / 合并 / 删除 / 替换）。任何改动落地前逐条自检；与本节冲突的一律不做，或先报用户决定。

1. **只增不退**：迭代只能让技能比现有能力更**强**，不允许比现有能力退步。
   不得削弱或删除已生效规则；确需用新规则替换旧规则时，新规则必须**完整覆盖旧规则的适用场景**，
   并在 CHANGELOG 写明「替换关系 + 覆盖度核验结论」。禁止以「简化 / 精简」为名做净减法。
2. **三场景核心能力覆盖**：技能必须持续覆盖三大场景（场景一 搭建 / 场景二 同步 / 场景三 审计）的核心能力。
   每轮收尾自检两项：① 本轮改动直接或间接增强了哪个场景；② 是否有场景被改动波及而弱化——发现弱化立即回滚该改动。
3. **频次优先：低频个例不直接采纳**：来自个例项目反馈反哺的经验卡，**不具备中高频使用场景的，原则上不直接采纳**；
   最多登记为「留待观察」（跨月跟踪项 TR-02），待后续在 ≥2 个不同项目 / 场景自然复现后再评估是否入档。
   频次判据（高→低）：**每次任务都会遇到**（如 ID 复核、空值兜底）> **隔几次任务遇到**（如幂等重试、限流退避）> **个例项目特有**（如某表特有字段结构）——第三档默认只观察、不入档。

## 三、可改文件（白名单 / 灰名单 / 红线）
- **白名单（复盘可直接建议改）**：references/*.md、scenarios/*.md、templates 示例、evolution/*。
- **灰名单（需用户显式同意）**：SKILL.md 正文流程/分支段落。
- **红线（不可改）**：
  - frontmatter `name`；assets/ 两份风格原文；
  - 有多次实测支撑的规则不可因单次抱怨推翻（冲突先呈报用户）；
  - 经验卡与写入内容一律脱敏；
  - scripts 改动需用户显式同意并走同一备份/回滚流程。

## 四、frontmatter 触发词规则（Q6 结论，保守原则）
- 只维护「与钉钉 AI 表格强相关」的触发词（建表/同步/审计/AI表格/dws 等）；
- **不加入歧义词**（如"台账/表格/数据"等其它场景共用词）——同事应使用 `@dingtalk-aitable-assistant` 显式调用；
- 若发现某新表达需扩为触发词：提交用户确认后才改 description（灰名单）；职责描述长句改动需更大范围确认。

## 五、落地流程（棘轮 + 人在回路）
1. 生成经验卡（模板见 cards 文件头部），含建议落点；
2. 向用户展示候选摘要 → 用户确认采纳/忽略；
3. 采纳：先复制原文件到 `backups/<时间戳>_<文件名>`（备份失败则中止）→ 写入 → cards 归档 → CHANGELOG 追加 → version 对应位 +1；
4. **一次只采纳 1 条**（便于归因与回滚）；
5. 回归：后续同类任务自然验证；若倒退 → 用 backups 快照还原 + CHANGELOG 记 `ROLLBACK EV-xxx`。

## 六、版本策略
- `X.Y.Z`：Z=规则采纳/勘误；Y=场景流程级调整；X=架构级（需另行评审）。
