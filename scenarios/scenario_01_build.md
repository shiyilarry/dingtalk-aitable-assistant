# 场景一：需求 → 方案档案 → 搭建 → 验收（Playbook）

## 触发
"帮我建一个XX表 / 我需要一个XX管理表 / 一句话式模糊需求" / 对既有 Base 提出升级、补功能（同一项目归入原档案演进）

## ⚠️ 流程铁律：先方案后开工（顺序不可颠倒）
1. 必须先产出**项目设计方案 HTML 档案（评审中态）**给用户；不先建任何表。
2. 评审可多轮：**同一文件演进**（正文=最新定稿，意见摘要入「评审与决策记录」10.2，待确认项在 10.1 打勾收口）；状态徽章保持「评审中」直到用户明确确认"最终版"。
3. **用户明确确认最终版后**才进入 S4 执行搭建；实施完成后把「示例数据与验收交付」追加进同一档案，徽章转「已交付」。
4. 反哺/测试类开发如需先建表验证 CLI 能力，必须标注"脚手架验证"，不得替代正式方案档案；脚手架结果应反哺 references（实测为准）。
5. 结构、措辞、状态徽章与渲染规范一律遵守 `references/report_style_guide.md`（锁定版 v2.0）。
6. **禁止静默降级（2026-09-23 补入）**：实现必须与已确认设计一致——图表/组件/模块的**数量与形态不得自行削减**；遇能力未验证项，先告知用户并给出回退方案，经确认后才调整范围（教训：曾自行把 6 张指标卡减为 4 张且未向用户说明 = 违规）。

## 子阶段
### S1 需求收集（必做）
- 收集：业务背景 / 核心字段(≥5) / 谁填谁看 / 参考模板或系统 / 是否有现成需求材料（md/pdf/会议纪要/Excel 需求表或实际表/语音转写）。
- **版本追问**：询问 AI 表格版本（免费/企业/旗舰），影响行数与冷热方案；不确定→按免费版并在合规自查节标注假设。
- 模糊一句话需求：先给 2~3 个澄清问题；用户没答复时按行业惯例做合理假设，在报告「需求拆解」节标注「推断，待确认」并入 10.1 待确认清单。

### S2 方案设计（HTML 项目档案 · 评审中态）——交付物核心
按 report_style_guide §2 的 0-13 顶层章节组织（文档头+状态徽章+变更记录 / 需求拆解设计观 / 方案结论 / 总体架构(SVG 分层图+域表) / 口径规范 / 数据表建设(底配中结归+冷热+单源直查) / 自动化轨道 / 月度 SOP / 仪表盘设计 / 合规自查 / 评审与决策记录 / [示例验收=实施后追加] / 注意事项待实测 / 附录）。关键渲染硬要求：
1. 方案架构分层图/表间关系图用**内嵌 SVG**（含图题 figcap），多表多层项目必须画；
2. 表间关系用**真关联字段**（单向关联/双向关联/查找引用 filterUp/关联引用 lookup），禁止文本冒充；金额 currency、部门 department、人员 user；
3. 公式一律代码块 + **一键复制按钮**（含跨表公式写法、filterUp 配置、口径公式），禁止只写公式名；
4. 自动化链路画「触发条件→动作」轨道图（SVG 节点轨道），供用户 UI 人工搭建参考；
5. 仪表盘按用户意图三分支处理（默认模板 SVG 框架图 / 按用户需求 / 明确不要则省略），默认模板与口径见 guide §2.1-8；
6. 合规自查 4 类逐条给结论（版本容量/公式嵌套≤5层/跨表公式优先级最低/计算单元格<30%）。
7. **CLI 能力矩阵（2026-09-05 实测，勿再写"看板/视图需 UI"）**：
   - CLI 已支持：Base/Table/Field/Record 增删改查、关联字段（单向/双向）、filterUp 查找引用（直建）、视图（Grid/Kanban 等+filter/group 协议）、仪表盘、图表（widgets-example 模板→chart create，create-only 红线）、表单基础；
   - 仍 UI 专属：公式字段创建、按钮字段、自动化（无 automation 命令）、OCR、单选「同步其他表选项」；
   - 平台红线：dashboard 组件建好后禁止同盘反复 update/delete（大改整盘重建）。
   - 每条给 UI 步骤要点或 CLI 命令要点，见 references/dws_command_ref.md 实操纪要。

### S3 用户评审与确认（同一文件多轮）
- 展示档案等待评审；字段类型改动必须在确认前完成（创建后不可改）；可多轮。
- 每轮：把用户核心意见写进 10.2 摘要 → 修订正文 → 10.1 待确认项打勾/新增 → 徽章保持「评审中」。
- **用户回执"确认最终版"**（或明确同意）→ 徽章转「已确认」→ 才允许 S4。

### S4 执行搭建（幂等，按最终版）
1. 幂等：`base list` 查同名 Base → 复用或新建询问。
2. **建表通用规则（所有表适用，方案 §5 已逐表落实）**：
   - 首列即主字段（不可隐藏/删除）→ 首列放**有实际业务意义的字段**（名称/编码/日期/类型），禁止放自编序号/占位列；
   - 需要自编单号（业务需要或用户明确要求）时用界面字段类型「自动编号」（可作主键），但**不得建在首列**；该类型 CLI 可建性未核验，以界面建列为准（详见 references/aitable_field_types.md 约束 1-2）。
   - **主数据字典须有消费方（2026-09-23 补入）**：设计 SPU/SKU 等主档时须同时给出当下消费方（引用它的表 / 计数 / 图表）；暂无消费方的，在档案明确标注「人工维护位」并写明用途，不得建无主档。
3. `base create`（新 Base）→ 逐表 `table create --fields`（≤15 字段/次，多的用 `field create` 补）。
4. 建关联字段（`field create` type=unidirectionalLink/bidirectionalLink 实测可用）、只读聚合字段（lookup/filterUp 实测可直建，config 见 field_types）→ `field list` 取 fieldId。
5. `record create`（--records-file ≤100/批）写示例数据（含关联 linkedRecordIds、user/department 真实 id）。
6. 视图/仪表盘/图表若在方案内且用户需要：按 S4.5 执行（CLI 支持）。
7. UI 专属项（公式/按钮/自动化/OCR/选项同步）写入档案 11 章「遗留 UI 待办」，逐项给位置+步骤。

### S4.5 视图 / 仪表盘 / 图表（CLI 实测支持，用户需要时执行）
- 视图：`view create --view-type Grid/Kanban/… --name`；带筛选用已解协议 `{"filter":[{"operands":[fieldId,选项key],"operator":"eq"}]}`、分组 `{"group":[{"fieldId":..,"direction":"ASC"}]}`（详见 dws_command_ref 实操纪要）。
- 仪表盘+图表：`dashboard create --name` → `chart widgets-example` 取模板（chartType/colors 必须用示例值、config 只用模板键集禁臆造字段）→ `chart create --config --layout`（**48 列网格**，同行 x+w=48、同行 h 一致、行连续）→ `dashboard get` 校验实体=布局零幽灵 → 输出仪表盘 URL（隐藏技术 id）。
- **红线**：同盘禁止反复 chart update/delete（update 不改 chartType 假象 / 实体随机丢失 / arrange 不清幽灵）；图表类型与关键配置 create 时一次定稿，大改=整盘重建（create-only）。
- 图表/仪表盘属交付能力演示时命名带「（示例）」；真实看板在用户确认口径后落地。
- 折线要点：多系列=LINE/STACKED_LINE + group；平滑= smooth:true + seriesSettingsBySheet.<sheet>.ALL_SERIES_VALUE.shape.lineSmoothType:"smooth" 两层；空值置零 nullValue:"zero"；数据点常显 symbolType:"always"。

### S5 测试验收（实施后追加进档案 §11）
- `field list` 核对字段类型；`record list` 抽查（含关联/查找引用实时计算值，filterUp 需显式 `--field-ids` 才返回值）；给出 Base 访问链接与验收摘要 → 把示例数据预览、验收清单、验收结论、遗留 UI 待办**追加**进同一方案档案（徽章→已交付）。

### S6 P5 复盘
- 收尾走 evolution 复盘（T1/T2/T3 → 候选卡 → 用户确认采纳）。
