# 报告 HTML 渲染与结构规范（锁定版 v2.0）

> 2026-09-07 用户拍板定稿：**报告交付从"多文件拆分"收敛为"单文件项目档案"**。
> - 方案类（场景一）= 一个 **演进式单文件档案**：设计方案 → 用户评审 → 实施 → 验收，全生命周期在同一 HTML 内追加推进；
> - 审计类（场景三）= 独立单文件，一次只读审计产出一份；同一项目二次审计同文件追加带日期审计节。
> - 除上述两类外，SKILL **不再产出**"用户评审单 / 执行交付报告单 / 同步方案拆分"等独立 HTML（场景二同步报告为任务性简要报告，可保留独立小报告）。
> 权威源 = `assets/PR_DESIGN.md`（方案视觉母本）、`assets/AR_DESIGN.md`（审计视觉母本）；本文件承载**内容结构与流程规约**（高于视觉母本的文档组织层）。

## 0. 视觉实现路线（2026-09-07 定稿）

- **UI 技术栈：Tailwind v4 + 适度动效**。渲染链路 = 内容 HTML（含 Tailwind utility class）→ `@tailwindcss/cli` 本地编译产出 CSS → **内联进 HTML** → 交付单文件**离线可开**（不依赖任何外网 CDN/字体/脚本运行时）。
- 视觉基准 = 已锁定「案例视觉（PR_DESIGN）」token（渐变 Hero、4 色语义、白卡、斑马纹、SVG 分层图）平移为 Tailwind `@theme` 变量（色板/圆角/字体/阴影），保证观感连续，不推翻重来。
- 动效"适度"三层：hero 渐入 / 区块 reveal（IntersectionObserver stagger ~70ms）/ hover 过渡（150ms）。不引入重量级动画库。
- 产物纪律：成品 HTML **不得出现** Clearbit/Resend/PR_DESIGN/AR_DESIGN/渲染引擎/渲染规范 等内部措辞；报告只呈现与项目需求直接相关的信息。
- 回退：若 Tailwind 构建链在某环境不可用，降级为手写静态 CSS 也要满足本文结构与视觉基调（内容完整性永远优先于工具）。

## 2. 方案类报告：单文件演进档案（结构总纲）

> 一个项目（同一 Base/业务域）= 一个 HTML 档案。文件命名固定：`YYYYMMDD_<项目主题>_设计方案.html`；**同文件覆盖演进**，不产生 v0.x 散件。页内以**状态徽章**表达阶段：`评审中 → 已确认 → 实施中 → 已交付`；用户明确确认"最终版"后徽章转为已确认，开始实施；实施完成、验收通过后转已交付。

### 2.1 顶层章节（评审阶段即全部出现，除标注"实施后追加"者）

0. **文档头**：类型 / 状态徽章 / 日期 / Base 访问链接（有则给）
+  **变更记录**：小表（日期 | 动作 | 摘要），随每次演进追加一行
1. **需求拆解与设计观**：需求来源清单（用户原话/材料）→ 拆解出的业务问题卡（用户没说但业务闭环必须的隐含场景要主动补全，并标注「推断，待确认」）→ 设计观（借鉴的业界模型与原因）
2. **方案设计与结论**：业务问题一句话 + 方案一句话 + 核心机制（如预算池/积分账本/冷热分层）+ 结论要点 chips
3. **总体架构**：① 内嵌 **SVG 架构分层图**（纵向分层 + 语义色卡 + 数据流箭头 + figcap 图题，底表→配置表→中间表→结果表→归档表等层级按项目实际）② 分层模块域 ↔ 各表映射（域卡）
4. **关键口径与配置规范**：字段级口径表 / 选项单一来源规范（singleSelect 同步其它表选项→源表+UI 步骤）/ 编号规则 / 金额·日期格式 / 防科学计数法 / 视图与仪表盘口径
5. **数据表建设方案**：按 **底表层 / 配置层 / 中间层 / 结果层 / 归档层**（按项目实际裁剪层名）逐层建表；每表 = 职责 + 全字段表（字段名/类型/选项/必填/口径/主键）+ 关联关系（单向/双向/查找引用 filterUp/关联引用 lookup，禁止文本冒充关联）+ 受限标注；归档层写清**冷热分层策略**（热=当月窗口，历史按月归档静态表）与**单数据源直查**（查找引用单源直查静态表，规避跨月多源）
6. **自动化流程设计**：每条自动化 = 触发条件/动作/落点表 + **可视化轨道图**（SVG 节点轨道：源表条件 → 动作 → 目标表写/改），供 UI 人工搭建参考
7. **每月操作 SOP**：人工每月操作步骤（第几步/操作对象/动作/注意）；**使用注意事项**（易错点）+ **长期可行的规避方案**
8. **仪表盘设计方案**：
   - 用户**未明确**仪表盘需求时：按默认模板出设计，用 **SVG 布局框架缩略图**（格子示意每行组件与宽度占比）直观展示，默认 5 行：R1 指标卡 3-5（**不含数值说明**，避免挤压数字）→ R2 结构图 2-3（饼/柱/条）→ R3 一张表格组件（左 ~70%）+ 一张雷达图（右 ~30%）→ R4 基础折线图（按核心字段分组多系列、默认平滑、默认空值置零）→ R5 底部表格组件；各行铺满无空缺、行行对齐
   - 用户**明确提出**仪表盘需求：严格按其需求拆解分析，给设计思路 + 布局图 + 口径；实现按 dws chart/dashboard 实测能力（见 dws_command_ref 实操纪要）
   - 用户**明确不需要**仪表盘：整节省略，不产出任何仪表盘设计与操作
9. **官方约束合规自查**（评审阶段必做，4 类逐条给结论 ✓/⚠/✗ + 依据）：
   - 版本容量：是否符合用户当前钉钉版本限制（免费版 2 万行/300 列/自动化 500 次每月 等；版本先追问，不确定按免费版）——若方案超限给出归档/分片策略
   - 公式复杂度：SWITCH/IFS 等条件公式嵌套 **>5 层**即告警，改用查表/拆分
   - 跨表公式：优先用查找引用/关联引用替代；**跨表公式方案选择优先级放最低**，避免计算压力
   - 计算密度：查找引用+公式单元格占全量 **>30%** 即预警（平台实测同万级单元格已吃力）；超限给出本地计算同步/静态结果表方案
10. **评审与决策记录**：10.1 当前待确认事项/待补充资料（编号 Q1…Qn，每项含"当前默认/建议"，评审期逐条打勾收口并回流到正文）；10.2 历史评审轮次摘要（每轮：日期/核心意见/采纳与驳回/正文 delta——**只存摘要不留旧全文**，正文永远最新定稿）
11. **示例数据与验收交付**（**实施后追加**进同一档案）：示例数据预览（10 条左右或适配条数，覆盖各状态/表关系/仪表盘口径，可顺链核验业务链）；验收清单（对照需求逐项 通过/部分通过/未通过 + 证据）；验收结论；Base 链接与可访问检查；遗留 UI 待办（公式/按钮/自动化/选项同步等逐项位置+步骤）
12. **注意事项与待实测项**：平台边界、本次未实测项、下轮验证计划（此节内容进入 EV 候选闭环）
13. **附录**：材料清单、术语、官方约束参考、字段/表索引

### 2.2 交付纪律
- 示例数据、真实字段、链接里的敏感信息一律脱敏（示例×× / 隐藏技术 id 只给实体名+链接）。
- 评审轮次之间，正文只允许"当前最新版"存在；过程意见入 10.2 摘要。
- 报告 HTML 是唯一交付载体；表格使用说明（doc_template）等补充文档可作为 Base 内说明，不作为独立交付件。

## 3. 审计类报告：结构（单次只读审计，评级总览置顶）

章节顺序（**评级总览必须是第一部分**）：
1. **评级总览**（第一部分，置顶）：综合评分（如 8.0/10）+ 总体结论一段 + 关键计数（问题 阻断级×n / 重要×n / 一般×n）
2. **范围与方法**：只读声明（零写操作）+ 审计对象（表清单）+ 审计方法说明
3. **需求与依据**：**多源需求依据**（不能仅靠单一纪要）——① 用户口述/文字需求与语音转写（注意 AI 转写可能省略细节，仅作线索）② 会议纪要/需求文档 ③ **Excel 需求表/模板/实际业务表及表内既有公式逻辑**（本地文件用只读提取，不修改）④ 其它（原型/截图/口头补充）；以**符合度矩阵**呈现：需求条目 × 依据来源 × 现状承接（符合/部分/缺失）
4. **覆盖核验**：逐条需求核验表（评级词：通过/部分通过/未通过，见 §5；每条带证据：字段/样例/依据原文）
5. **问题清单**：每条 = 级别 / 现状 / 影响 / 建议 / **关闭条件**；建议内区分 CLI 可执行与需 UI
6. **建议执行顺序**：按 阻断→重要→一般 排序的最小改动路径（无重大问题→良好评级+前瞻建议）
7. **（可选）项目优化建议**：仅当评估出比现状更优的实现方式时才加本模块；没有则整节不出现
8. **附录**：表结构概览（表名/字段数/字段清单/特殊列分布）

## 5. 审计评级措辞（2026-09-07 定稿：黑话改常规中文）

- 问题级别：**阻断级**（必须修复，原 P0）/ **重要**（建议修复，原 P1）/ **一般**（可优化，原 P2）——首次出现处用极小字括注原码 `（原 P0）` 便于对应，此后不再重复。
- 需求符合度 / 覆盖核验评级：**通过**（原 PASS）/ **部分通过**（原 PARTIAL）/ **未通过**（原 FAIL）。
- 同步报告统计：**新增/更新/跳过/失败**（不再用 N/M/K 黑话）。
- 报告中不出现任何网络化黑话或非标准缩写的堆叠。

## 6. 写作纪律（不变）
- 一个报告只呈现**结论与依据**，不叠加新旧版本说明/备注解释（评审历史按 10.2 摘要收纳，不进正文）。
- 真实项目名/ID/财务/品牌一律脱敏。
- 交付前自检：状态徽章正确 / 结构章节齐全（方案 0-13 或审计 1-8）/ 风格规范核对 / 高亮块有底色 / 无代码标签字面残留 / 无内部措辞（Clearbit/Resend/引擎等）/ 可离线打开 / 链接可访问。
